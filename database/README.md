## 一、总体分工

每人主责一个数据域（从实体识别到数据字典），共享成果按“谁主责谁起草、谁相邻谁交叉检查、组长统稿提交”的方式推进。

| 成员 | 主责数据域 | 主要表（建议，可随设计调整） | 对应需求与用例 |
|---|---|---|---|
| 庞华杰（组长） | 总体 ER 图框架与整合；用户与角色域 | `user`、`role`、`seller_profile` | FR-08、UC-05；统筹全部交付物 |
| 庞延新 | 花束与库存域 | `bouquet`、`category`、`bouquet_image`、`bouquet_stock` | FR-01～FR-04、UC-01/02/06/07 |
| 何奕佳 | 订单域 | `orders`、`order_item` | FR-05、FR-06、UC-03/08 |
| 林伟翔 | 订单状态与库存流水域 | `order_status_log`、`stock_change` | FR-07、UC-04/05；互评组织 |

分工原则：
1. 数据域边界与各人在实验一的主责用例一致，便于在报告中解释“我负责的部分如何落到表”。
2. 跨域字段（如 `bouquet.stock_qty` 与 `stock_change`、`orders.status` 与 `order_status_log`）由两个域的负责人共同定稿，接口写进数据字典，不由一方单方面修改。
3. 组长做实质设计（总体 ER、用户域、统稿、一致性核对），不只是收集文件。

## 三、必须落到设计里的业务约束

以下条目来自需求简表与既有规则记录，设计时必须有对应的键、CHECK、唯一约束或说明，走查时要能指出由哪张表哪条约束保证。

| 约束 | 设计要求 | 主责 |
|---|---|---|
| B-05 可预订数量非负，且与有效订单一致 | `bouquet.stock_qty` 加 `CHECK (stock_qty >= 0)`；扣减与回补由事务保证，写入 `stock_change` 流水 | 庞延新 / 林伟翔 |
| B-08 下单时记录单价快照 | `order_item.unit_price` 保存成交时价格，不随花束改价变化 | 何奕佳 |
| B-06 取消仅回补一次、历史订单保留 | 订单只改状态不删除；`order_status_log` 记录每次变更；重复取消不产生第二次回补 | 林伟翔 |
| 重复提交只产生一次业务效果（NFR-02） | `orders.idempotency_key` 唯一约束 | 何奕佳 |
| 仅本人可取消、他人订单不可见（NFR-03） | 订单与用户的外键关系；身份校验写清属应用层责任，不假设外键能完成越权判断 | 林伟翔 / 何奕佳 |
| 下架不影响历史有效订单（B-07） | 花束状态与订单分离，订单不因下架失效 | 庞延新 |
| 密码非明文 | 用户表只存哈希与盐，说明算法由实现层决定 | 庞华杰 |

**设计要点**：区分“同一花束有多条历史订单”与“顾客当前最多一个有效订单（如业务需要）”两种基数；外键只保证引用存在，身份校验和跨表状态更新要在设计说明里写明由应用或事务负责。

## 四、建模约定

1. 表名、字段名统一小写 `snake_case`；主键统一 `id`，外键为 `<被引用表>_id`；时间字段 `created_at`、`updated_at`。
2. 金额用 `DECIMAL(10,2)`，单位元；数量用 `INT`，单位束；字符集 `utf8mb4`。
3. 状态字段用 `VARCHAR` 加 `CHECK` 枚举，取值必须与用例中的状态名一致（有效 / 已取消 / 已完成；已上架 / 已下架（待上架））。
4. 每张表在数据字典中必须写清：表用途、字段含义、类型与长度、可空性、默认值、主外键、其他约束。
5. 变更先在 Issue 或提交说明里写原因，再改图与字典，保证三者（ER、字典、关系图）同版本。
