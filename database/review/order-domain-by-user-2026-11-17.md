## 2 具体意见

### O-01 总体 ER 的 R7 基数需同步为 1:1（已在本次修订处理）

- **位置**：`er/er-overall.md` 第 4 节 R7 原写“1:1..N”，与订单域 v0.3 的 `UNIQUE(order_id)` 不一致。
- **处理**：本次 ER 升 v0.2，R7 改为 1:1，并同步 PNG；不属订单域问题，记录在此便于追溯。

### O-02 `total_amount` 与明细合计的等值关系未写明（建议，不阻塞）

- **位置**：`order.md` 第 2 节 `total_amount` 约束只有 `>= 0`；第 3 节 `amount` 已有 `CHECK (amount = ROUND(quantity * unit_price, 2))`。
- **问题**：一行明细时 `total_amount = amount` 成立，但这条等式跨表，CHECK 表达不了；文档目前只在“金额上限”处解释精度，没有说明总额如何与明细对账。
- **建议**：在 `order.md` 第 2 节“其他约束与说明”补一句：**`total_amount` 由下单事务写入，本期等于唯一明细的 `amount`；跨表等值由事务保证，可用对账查询发现不一致**。若后续支持一单多花束，改为“等于明细之和”。

### O-03 取消幂等键与状态条件更新的配合（确认，符合）

- `cancel_idempotency_key` 唯一且可空，未取消时为 NULL；同一取消请求重试命中同键返回首次结果，不同键的重复取消由 `WHERE status='有效'` 影响 0 行挡住，不会二次回补。与 `stock_change` 的 `UNIQUE(order_id, change_type)` 构成两道保险，口径正确。

### O-04 一单一明细的扩展边界（确认，符合）

- `UNIQUE(order_id)` 强制本期一单恰好一条明细；扩多花束需改为 `UNIQUE(order_id, bouquet_id)` 并同步流水去重粒度，`order.md` 第 3 节已写明迁移条件，属于可执行的说明，不是隐式假设。

### O-05 越权与状态日志（确认，符合）

- 订单归属只靠 `orders.user_id`，越权判断明确交给应用层；状态变化与 `order_status_log` 同行数写入的要求写在跨域接口表，与流水域一致。

## 3 与本域接口的互认

| 接口 | 订单域用法 | 确认结果 |
|---|---|---|
| `user.id` 类型与语义 | `orders.user_id` 外键 | **一致**：`BIGINT UNSIGNED`；账号不删除，`ON DELETE RESTRICT` 不会误删订单 |
| `user.role_id = 1` | 下单前置条件 | **一致**：订单域不重复校验角色，依赖登录态带入 |
| `user.status = '停用'` | UC-03 A1 的拒绝分支 | **一致**：已按 D-06 在用户域明确“停用后拒绝登录；其在架花束联动下架”，订单域只需在 A1 的“会话失效/角色不符”旁并列“账号已停用” |
| `seller_profile` | 订单域不引用 | 无接口 |
