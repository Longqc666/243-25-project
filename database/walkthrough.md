> 依据：`database/README.md` T10 与实验二指导书第三步第 5 条
> 分工：**正常下单（何奕佳）**、取消后再次下单（林伟翔）、库存不足与并发边界（庞延新）

## 1 走查口径

每个场景按"给定数据 → 操作 → 预期变化 → 约束依据"四段记录，全部使用虚构数据。表名与字段以 `database/schema/` 下各域数据字典 v0.1 为准；涉及多域时写明由哪个事务一并完成。

## 2 场景 S1：正常下单（本人主责）

### 2.1 给定数据

| 对象 | 取值 |
|---|---|
| 顾客 C | `user.id = 10`，角色=顾客，已登录 |
| 花束 A | `bouquet.id = 1`，单价 199.00 元/束，`stock_qty = 5`，状态=已上架 |
| 请求 | 数量 2 束，送达日期 2026-11-18，履约方式=自提，幂等键 `K1` |

### 2.2 操作

顾客在花束 A 的详情页提交预订。系统在同一事务内完成：幂等判重 → 写订单 → 写明细 → 条件扣减库存 → 写库存流水 → 写状态日志。

### 2.3 预期变化

| 表 | 预期结果 |
|---|---|
| `orders` | 新增 1 行：`id=100`、`order_no=SO202611150001`、`user_id=10`、`status='有效'`、`total_amount=398.00`、`delivery_date=2026-11-18`、`fulfillment_type='自提'`、`idempotency_key='K1'`、`cancelled_at=NULL` |
| `order_item` | 新增 1 行：`order_id=100`、`bouquet_id=1`、`quantity=2`、`unit_price=199.00`（快照）、`amount=398.00` |
| `bouquet` | `stock_qty` 由 5 变为 3（`UPDATE ... SET stock_qty = stock_qty - 2 WHERE id = 1 AND stock_qty >= 2`，影响 1 行） |
| `stock_change` | 新增 1 行：`bouquet_id=1`、`order_id=100`、`change_type='下单扣减'`、`quantity_delta=-2`、`before_qty=5`、`after_qty=3`、`user_id=10` |
| `order_status_log` | 新增 1 行：`order_id=100`、`from_status=NULL`、`to_status='有效'`、`user_id=10` |

### 2.4 约束依据

| 检查点 | 由什么保证 | 引用 |
|---|---|---|
| 同一请求只生成 1 单 | `uk_orders_idem` 唯一键；重复请求在插入阶段冲突 | NFR-02、AC-UC03-06 |
| 数量在 1—99 | `ck_item_qty` CHECK | Q-02 |
| 金额取快照、不受改价影响 | `order_item.unit_price` 写入后不更新 | B-08 |
| 剩余量不为负、不超卖 | `bouquet.stock_qty >= 0` + 条件更新（影响行数为 0 则整体回滚） | B-05、NFR-01 |
| 扣减有据可查 | `stock_change` 每笔扣减一行，`after_qty` 与 `bouquet.stock_qty` 同事务一致 | G3 |
| 状态变更可追溯 | `order_status_log` 写"创建"流水 | G3；流水域待确认项 1 |
| 跨表一致性 | `stock_change.bouquet_id` 必须等于 `order_item.bouquet_id`，MySQL 无跨表 CHECK，由事务带出（应用层责任） | 实验二指导书"检查重点" |

## 3 场景 S2：同一请求重试（边界，本人主责）

### 3.1 给定数据

| 对象 | 取值 |
|---|---|
| 前置 | 场景 S1 已完成，订单 100 已存在，A 的 `stock_qty = 3` |
| 极值前置 | 另一情形：A 只剩 1 束，S1 已把最后一束订走，`stock_qty = 0` |
| 请求 | 同一幂等键 `K1` 的请求再次到达 2 次（重复点击或断网重试） |

### 3.2 操作

请求到达系统，第 1 次校验登录，随后进行幂等判重；命中 `K1` 后直接返回已有订单。

### 3.3 预期变化

| 表 | 预期结果 |
|---|---|
| `orders` | 不新增行（唯一键冲突被捕获），返回 `id=100` 的订单 |
| `order_item` | 不新增行 |
| `bouquet` | `stock_qty` 保持 3（或极值情形下保持 0），不再扣减 |
| `stock_change` | 不新增行；`UNIQUE(order_id, change_type)` 再兜一层 |
| `order_status_log` | 不新增行 |

### 3.4 约束依据

- NFR-02：同一提交请求重复到达只产生 1 次业务效果；落点是 `orders.idempotency_key` 唯一键，`stock_change` 的唯一约束为第二道保险。
- **顺序约束**：判重必须先于库存校验。若先校验 `stock_qty > 0`，极值情形下（剩余为 0）重试会被判为"售罄"，用户看不到自己已成功的订单——这正是实验一互评在 UC-03 中指出的问题，已通过把判重提前到第 3 步修正（提交 `6f9c752`）。
- 实证条件：需构造两次相同幂等键的请求（重复点击、断网重试），核对订单数恒为 1、`stock_qty` 只减少一次。**本场景未执行 SQL，结论为设计推演。**

## 4 与相邻场景的衔接

| 场景 | 主责 | 与本场景的关系 |
|---|---|---|
| 取消后再次下单 | 林伟翔 | S1 生成的订单 100 被取消后，`stock_qty` 回补、`stock_change('取消回补')` 写入；再次下单生成新订单，幂等键不同 |
| 库存不足与并发边界 | 庞延新 | S1 的"条件扣减"是该场景的核心：两个请求同时命中 `stock_qty >= N`，只有一个影响 1 行 |

**本场景触及的跨域一致性**：`stock_change.bouquet_id` 与 `order_item.bouquet_id` 必须相同；`orders.status` 变化必须与 `order_status_log` 同行数写入。两条都由下单/取消事务保证，MySQL 层面无跨表约束。
