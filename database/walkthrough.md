## 1 走查口径

每个场景按"给定数据 → 操作 → 预期变化 → 约束依据"四段记录，全部使用虚构数据。表名与字段以 `database/schema/` 下各域数据字典 v0.1 为准；涉及多域时写明由哪个事务一并完成。

## 2 场景 S1：正常下单（本人主责）

### 2.1 给定数据

| 对象 | 取值 |
|---|---|
| 顾客 C | `user.id = 10`，角色=顾客，已登录 |
| 花束 A | `bouquet.id = 1`，单价 199.00 元/束，`stock_qty = 5`，状态=已上架 |
| 请求 | 数量 2 束，送达日期 2026-11-18，履约方式=自提，幂等键 `K1` |

### 2.2 操作

顾客在花束 A 的详情页提交预订。系统在同一事务内完成：幂等判重 → 写订单 → 写明细 → 条件扣减库存 → 写库存流水 → 写状态日志。

### 2.3 预期变化

| 表 | 预期结果 |
|---|---|
| `orders` | 新增 1 行：`id=100`、`order_no=SO202611150001`、`user_id=10`、`status='有效'`、`total_amount=398.00`、`delivery_date=2026-11-18`、`fulfillment_type='自提'`、`idempotency_key='K1'`、`cancelled_at=NULL` |
| `order_item` | 新增 1 行：`order_id=100`、`bouquet_id=1`、`quantity=2`、`unit_price=199.00`（快照）、`amount=398.00` |
| `bouquet` | `stock_qty` 由 5 变为 3；`version` 递增、`updated_at` 刷新（`UPDATE bouquet SET stock_qty = stock_qty - 2, version = version + 1, updated_at = NOW() WHERE id = 1 AND status = '已上架' AND stock_qty >= 2`，影响 1 行） |
| `stock_change` | 新增 1 行：`bouquet_id=1`、`order_id=100`、`change_type='下单扣减'`、`quantity_delta=-2`、`before_qty=5`、`after_qty=3`、`user_id=10` |
| `order_status_log` | 新增 1 行：`order_id=100`、`from_status=NULL`、`to_status='有效'`、`user_id=10` |

### 2.4 约束依据

| 检查点 | 由什么保证 | 引用 |
|---|---|---|
| 同一请求只生成 1 单 | `uk_orders_idem` 唯一键；重复请求在插入阶段冲突 | NFR-02、AC-UC03-06 |
| 数量在 1—99 | `ck_item_qty` CHECK | Q-02 |
| 金额取快照、不受改价影响 | `order_item.unit_price` 写入后不更新 | B-08 |
| 剩余量不为负、不超卖 | `bouquet.stock_qty >= 0` + 条件更新（同时校验 `status='已上架'` 与余量，影响行数为 0 则整体回滚） | B-05、NFR-01；接口核对 I-07 |
| 成交价与花束版本一致 | 在读取到的 `version` 上扣减并递增；旧表单提交未命中版本即拒绝 | I-07；花束域 `bouquet.version` |
| 扣减有据可查 | `stock_change` 每笔扣减一行，`after_qty` 与 `bouquet.stock_qty` 同事务一致 | G3 |
| 状态变更可追溯 | `order_status_log` 写"创建"流水 | G3；流水域待确认项 1 |
| 跨表一致性 | `stock_change.bouquet_id` 必须等于 `order_item.bouquet_id`，MySQL 无跨表 CHECK，由事务带出（应用层责任） | 实验二指导书"检查重点" |

## 3 场景 S2：同一请求重试（边界，本人主责）

### 3.1 给定数据

| 对象 | 取值 |
|---|---|
| 前置 | 场景 S1 已完成，订单 100 已存在，A 的 `stock_qty = 3` |
| 极值前置 | 另一情形：A 只剩 1 束，S1 已把最后一束订走，`stock_qty = 0` |
| 请求 | 同一幂等键 `K1` 的请求再次到达 2 次（重复点击或断网重试） |

### 3.2 操作

请求到达系统，第 1 次校验登录，随后进行幂等判重；命中 `K1` 后直接返回已有订单。

### 3.3 预期变化

| 表 | 预期结果 |
|---|---|
| `orders` | 不新增行（唯一键冲突被捕获），返回 `id=100` 的订单 |
| `order_item` | 不新增行 |
| `bouquet` | `stock_qty` 保持 3（或极值情形下保持 0），不再扣减 |
| `stock_change` | 不新增行；`UNIQUE(order_id, change_type)` 再兜一层 |
| `order_status_log` | 不新增行 |

### 3.4 约束依据

- NFR-02：同一提交请求重复到达只产生 1 次业务效果；落点是 `orders.idempotency_key` 唯一键，`stock_change` 的唯一约束为第二道保险。
- **顺序约束**：判重必须先于库存校验。若先校验 `stock_qty > 0`，极值情形下（剩余为 0）重试会被判为"售罄"，用户看不到自己已成功的订单——这正是实验一互评在 UC-03 中指出的问题，已通过把判重提前到第 3 步修正（提交 `6f9c752`）。
- 实证条件：需构造两次相同幂等键的请求（重复点击、断网重试），核对订单数恒为 1、`stock_qty` 只减少一次。**本场景未执行 SQL，结论为设计推演。**

### 3.5 同一幂等键并发到达（补充，回应接口核对 I-09）

两个携带同一 `K1` 的请求几乎同时到达时，若无唯一键，预查询可能都查不到、都去扣库存。正确结果是：

| 阶段 | 预期 |
|---|---|
| 两个请求都通过登录与判重预查 | 预查不能作为最终依据 |
| 插入 `orders` | 唯一键 `uk_orders_idem` 只允许一条成功，另一条整笔事务回滚（含其库存扣减与流水） |
| 回滚方 | 按 `K1` 重新查询已提交的订单，返回同一订单号与金额，不提示售罄 |

约束依据：NFR-02 由唯一键保证，不依赖"先查后写"；失败方回滚保证 `stock_qty` 只减一次。与庞延新 S7 的口径一致，两处互为印证。

## 4 与相邻场景的衔接

| 场景 | 主责 | 与本场景的关系 |
|---|---|---|
| 取消后再次下单 | 林伟翔 | S1 生成的订单 100 被取消后，`stock_qty` 回补、`stock_change('取消回补')` 写入；再次下单生成新订单，幂等键不同 |
| 库存不足与并发边界 | 庞延新 | S1 的"条件扣减"是该场景的核心：**剩余量足够时两个请求都能成功**；只有剩余不足（如最后 1 束）时，才只有一个命中 `stock_qty >= N` |

**本场景触及的跨域一致性**：`stock_change.bouquet_id` 与 `order_item.bouquet_id` 必须相同；`orders.status` 变化必须与 `order_status_log` 同行数写入。两条都由下单/取消事务保证，MySQL 层面无跨表约束。

### 与原S1/S2的接口衔接

本节最终对照main e7e1d78及README D-01～D-05。业务主外键BIGINT UNSIGNED；商家归属bouquet.seller_id→user.id。D-03已定订单三值占位、D-04已定系统库存流水user_id可NULL、D-05已定保留快照/合计及库存当前值与流水并存，不再作为本轮未决项。创建日志首条NULL前状态及业务防重细节仍由对应负责人同步。

- 当前价为`bouquet.price`；成交价为`order_item.unit_price`，行金额为`order_item.amount`，合计为`orders.total_amount`。原S1的199×2=398保持不变；之后改价209，历史199/398不变。成交价读取与扣减应在一致的花束版本内完成。
- 原S1只展示余量条件。本域建议最终写入同时检查仍为已上架，并递增`version`、维护`updated_at`，待与订单负责人统一。S2成功请求重试不改库存、版本、订单或流水。
- 先身份及请求归属检查，再识别成功请求，之后才校验新请求的库存。同键同时到达还需S7的唯一键冲突恢复，不能只查询一次是否存在。
- 按订单v0.2“一单一种花束”推演。`UNIQUE(order_id,bouquet_id)`未独自强制每单一行，需要应用/事务保证或共同加强约束；扩多种前同步流水粒度。
- 以下version为本域方案预期，尚待相邻负责人采纳。NULL→有效的创建日志沿用原S1，流水负责人仍需关闭其对应待确认项。

给定：X已上架，余量0、version=10；O1属于A，有效，唯一明细为X两束，quantity=2；送达日期D+1，A在D当天取消，满足UC-04第6节送达日0:00前的规则。其他Q-03日期算法保持待定。

| 顺序 | 操作 | 余量/版本 | 订单与流水预期 |

| 1 | A以取消请求C1成功取消O1 | 2 / 11 | O1已取消，cancelled_at写一次；原明细不删不改；有效→已取消日志及取消回补(0,+2,2)各1条 |

### S5 部分写入失败后整体回滚（本人补充）

给定：X余量3、version=30，新请求订2束，其余条件合法；未提交事务已将余量暂改为1。

操作：订单、明细、状态日志或库存流水任一步写入失败。

预期：整笔回滚，X仍余量3、版本30；无新增成功订单、明细及成功流水。自增编号可有空洞，不能用编号连续判断一致性。失败后按实际提交状态处理重试，不将未提交记录当作成功。

约束依据：事务原子性、UC-03失败后保证。取消回补失败同理：订单仍有效，不写成功取消时间，库存保持原量；不得出现已取消但未回补（UC-04 A6）。

### S6 商家改量与下单并发（本人补充）

给定：商家读取X余量10、version=40，准备设为3；顾客新请求同时订3束。已有订单占用数不是商家改量下限。

| 操作先后 | 预期变化 | 约束依据 |
|---|---|---|
| 下单先提交 | 余量7、版本41，扣减流水(10,-3,7)。商家用旧版本40/旧量10提交失败，提示刷新；库存仍7，不记商家成功调整流水 | UC-07 A11；旧表单不能覆盖已提交变化 |

### S7 相同下单请求同时到达（本人补充，待何奕佳确认）

给定：X余量2、version=50；A同一个新请求K3同时到达两次，各订1束，两个事务都可能在预查询时未找到成功订单。
