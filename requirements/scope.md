# 系统概述与范围（鲜花预订与交易平台）


## 业务背景与问题

校园周边的鲜花消费高度集中在节日与纪念日：情人节、母亲节、毕业季、教师节前后需求陡增，平日相对平缓。目前周边花店普遍通过微信群、朋友圈图片和电话接单，花束图片、价格与当日可预订数量分散在不同聊天记录里，顾客只能反复询问"这款还有没有""明天能不能送到""能不能换一种包装"；商家则用纸笔或表格登记订单，节日高峰时容易出现同一批花束被重复承诺、顾客临时取消后库存没有回补、改期与取消记录互相覆盖等情况。

本项目的业务问题可概括为三点：

1. **信息与库存不透明**：花束的花语、适用场景、单价、可预订数量没有集中登记，顾客无法自助判断"能不能订、什么时候能送到"，商家也说不清当天到底还能接几单。
2. **预订与库存缺少一致性约束**：口头承诺没有量化的占用机制，同一花束可能被超量预订，节日当天才发现花材不够。
3. **取消与状态变更缺少统一规则**：谁可以取消、取消后库存如何回补、历史订单如何保留，目前都依赖人工记忆，一旦发生争议无据可查。

## 系统目标与使用方式

### 系统目标

- **G1 花束信息集中、可自助检索**：商家按"一条发布 = 一种花束（含可预订数量）"登记，顾客按花名、花语/适用场景、价格区间等条件自主检索并查看详情。
- **G2 预订与库存一致**：下单表示预订并占用库存，“可预订数量”统一表示剩余可预订数量（单位：束）。每笔成功预订扣减本次数量且剩余量不为负；成功取消仅回补一次原订单数量。商家调整剩余量不改变已有订单。
- **G3 全过程留痕**：订单记录下单时的单价快照与送达日期，取消不删除记录，历史订单可查，改价不影响已产生的订单。
- **G4 角色边界清晰**：顾客、商家、平台管理员各自可见的功能入口与数据范围相互隔离，越权操作被拒绝。

**非目标**：系统不完成真实交易，不涉及资金流、物流履约与信用评价；本期只回答"能不能订、订了几束、谁取消的"，不回答"钱怎么付、花怎么送到"。

### 使用方式

- **形态**：浏览器访问的 Web 应用（B/S），前端 + 后端服务 + MySQL 持久化；顾客端与商家端共用一套界面，按登录角色展示不同入口，平台管理员使用管理端。
- **身份**：使用预置测试账号登录，不提供注册、找回密码、实名认证与第三方登录；同一账号在同一时刻只有一种角色。
- **典型路径**：商家登录 → 发布花束（暂定默认下架）→ 上架 → 顾客检索 → 查看详情 → 选择数量、送达日期与自提/配送方式并预订 → 库存扣减、订单置为"有效" → 顾客（必要时）取消 → 订单置为"已取消"、库存回补。
- **数据**：花束、订单与订单状态变更均落库；历史订单只增不删；订单金额以单价快照为准。

| 角色     | 说明                 | 目标                      | 主要用例                         |

| 商家     | 花店的花艺师或店员，使用预置员工账号 | 把花束卖出去，并管好可预订数量与上下架     | 发布花束、编辑与上下架、调整可预订数量、查看本店订单   |

## 排除范围

- **真实支付与资金**：在线支付、退款、发票、商家结算与对账。
- **物流与履约**：物流跟踪、配送进度查询、运费计算，以及商家接单、备货、交付确认等履约环节。
- **交易完成与售后**：订单"完成"的确认流程、售后与纠纷处理。
- **评价与推荐**：评价、晒图、评分、排行榜与个性化推荐。
- **营销与会员**：优惠券、积分、会员等级、节日活动配置。
- **账号管理**：注册、找回密码、实名认证、第三方登录（仅使用预置测试账号）。
- **内容业务**：直播、社交互动、花艺课程等与预订链路无关的功能。

边界影响：因排除"交易完成"，订单不存在由系统推进的履约流转，状态集合是否保留"已完成"占位见 Q-10；因排除支付，订单金额只是意向价格，不产生任何资金动作。

## 基本约定

以下约定作为共同分析口径；尚未明确的细节统一记入下文待确认问题。2026-11-07，庞延新在本次协作对话中确认“小组已同意”检索与详情规则建议，落实范围及后续事项见[规则记录](../records/rules-uc02-uc06-2026-11-07.md)。这项确认不代表程序测试或正式互评已通过。

- **B-01** 范围为发布花束、检索与查看、预订下单、取消订单四项核心业务。
- **B-02** 使用预置测试账号登录；注册、找回密码、实名认证等账号管理不纳入本次范围。
- **B-03** 平台采用"入驻花店/自营商家发布"的模式，由商家发布花束；同一账号在同一时刻只有一种角色。
- **B-04** 一条发布代表一种花束（含可预订数量）；下单表示预订并占用库存，不表示付款。
- **B-05** 所有计价与数量统一按“束”。“可预订数量”表示当前剩余可预订数量，而非包含已占用部分的总容量。下单须满足本次数量不超过当前剩余量，成功后扣减 N 束；取消成功回补原订单 N 束且仅一次，失败均不改变数量；剩余量始终不为负。商家改量设置的是新的剩余量，不以有效订单占用数作为下限，不改变已有订单。
- **B-06** 仅订单所属顾客本人可以取消该订单；取消后订单失效、库存回补，历史订单保留。
- **B-07** 不接入真实支付、退款、物流跟踪与运费计算、评价、推荐与发票；订单只记录送达日期与自提/配送方式。
- **B-08** 订单金额以下单时的单价快照为准，商家后续改价不影响已产生的历史订单。

## 场景讨论

| 场景 | 情境 | 需要说明的问题 |
|---|---|---|
| **S-01 发布** | 花艺师小林准备上架一款“向日葵思慕”花束。 | 至少提供哪些信息？缺图片、缺价格时应得到什么反馈？发布后是否立即对顾客可见？ |
| **S-02 检索** | 顾客小周想找 200 元以内、适合表白的红色系花束。 | 支持什么检索条件？结果列表与详情页分别需要展示什么（库存、最早可送达日期）？ |
| **S-03 预订** | 小周选中一款可预订 3 束的花束，订 2 束并要求周六送达。 | 成功后顾客看到什么？库存与订单分别意味着什么？价格按哪一次为准？ |
| **S-04 竞争** | 小周和小陈几乎同时预订最后 1 束。 | 可以有几个有效订单？未成功的一方应收到什么反馈？库存最终是多少？ |
| **S-05 取消** | 小周取消订单，随后小陈重新预订同一束花。 | 旧订单如何保留？旧取消请求再次到达时，会不会重复回补库存或影响新订单？ |
| **S-06 越权** | 小陈尝试取消小周的订单。 | 谁可以执行取消？拒绝后订单、库存与顾客信息中哪些必须保持不变？ |
